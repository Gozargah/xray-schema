Automatically binds Xray outbounds to a physical network interface, so that traffic generated by Xray itself is not sent back into the TUN interface and looped.

If a connection cannot be bound to that interface, it fails instead of leaving unbound, where it could loop back into the TUN interface. On Windows, an interface with only IPv4 or only IPv6 works as well: connections of the missing IP version fail, rather than leaving through another interface.

Connections to loopback addresses are not bound. On FreeBSD, Xray's connections are switched to a second routing table (FIB 1) that mirrors the physical default route instead, which needs the boot tunable `net.fibs` set to at least 2, otherwise Xray does not start.

On Windows, this binding only holds while that interface has weak host send and forwarding off for the IP versions routed to the TUN interface; otherwise Windows sends Xray's own connections into the TUN interface, where they stall. Xray therefore turns weak host send off on that interface while the TUN interface runs, and on again when it stops. Forwarding, which Mobile Hotspot and Internet Connection Sharing need, is left alone, and a warning is logged instead: have the hotspot share the TUN interface (Settings → Network & internet → Mobile hotspot → Share my internet connection from), which also sends the hotspot's devices through Xray. The TUN interface only appears in that list while Xray is running.

Equivalent to automatically setting [sockopt](https://xtls.github.io/en/config/transports/sockopt.html).interface for all outbounds (it also additionally covers some requests that cannot have outbound settings configured, such as the various local modes of the built-in DNS), which can be overridden by manually set sockopt.

The default value is `null`, which means not configured. You can specify an interface name explicitly, or use `"auto"` to let Xray choose one automatically. If `autoSystemRoutingTable` is configured but this field is omitted, Xray treats it as `"auto"`.
